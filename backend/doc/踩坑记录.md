# backend 踩坑记录

记录本项目实际遇到或验证过的问题，按「现象 → 原因 → 处理 → 依据」写。
重构 / 报错时先查这里。

---

## A. 数据库与模型

### A1. `create_all` 不会给存量表补列

**现象**：给 `User` 新增 `avatar` 后，老库启动不报错，但查询报列不存在。

**原因**：SQLAlchemy `Base.metadata.create_all` 只建缺失的**表**，不改已有表结构。

**处理**：`core/database.py::init_db` 在 `create_all` 后执行幂等迁移：

```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS avatar VARCHAR(500)
```

后续新增列同样要显式补迁移，不能只改模型。

### A2. 种子数据不能覆盖管理员改过的配置

**现象**：重启后超管改过的默认设置被改回初始值。

**原因**：种子逻辑如果无条件 upsert，就会覆盖运行时数据。

**处理**：`async_seed` 只插入缺失行；角色权限只做“补新权限点 + 剔除超管专属项”的兼容更新。

**依据**：`core/seed.py` 中每个 key 先 `session.get`，存在即跳过。

### A3. 角色权限升级遗漏新权限点

**现象**：v0.2.0 增加 `permissions.self` 后，老库里的 `user` 角色没有该权限，菜单不显示“我的权限”。

**原因**：角色权限行已存在，种子不会重建。

**处理**：种子启动时给非超管角色补 `permissions.self`，给 `admin` 补 `permissions.team`，并把超管角色刷新为全部权限点。

## B. 权限模型

### B1. 临时越级授权被“可分配权限”过滤

**现象**：超管给李四设置临时 `system.status`，保存成功但 `temp_grants` 恒为空。

**原因**：`async_admin_set_state` 最初用 `ASSIGNABLE_PERMISSION_KEYS` 过滤临时授权，而 `system.status` 是 `super_only`，被直接丢弃。

**处理**：临时授权改用 `ALL_PERMISSION_KEYS` 校验；永久 `granted` 与 `shrunk` 仍只允许可分配权限点。

### B2. 临时授权有了权限却仍然 403

**现象**：李四通过临时授权拿到 `system.status`，`/auth/me` 能看到，但 `/api/system/status` 返回 403。

**原因**：路由依赖仍是 `SuperAdmin`，不认临时授权。

**处理**：运行状态接口改为 `Depends(require_permission("system.status"))`；用户管理/默认设置仍保持超管专属。

### B3. 收缩权限后菜单不刷新

**现象**：上级收缩李四的 `profile` 后，李四当前页面菜单仍在。

**原因**：前端菜单来自登录时缓存的 `/auth/me`。

**处理**：前端收缩成功后调用 `auth.fetchMe()`；服务端每次请求仍按数据库实时校验，缓存只影响显示。

### B4. 收缩集合与临时授权冲突

**处理原则**：`shrinkable` 计算时排除 `temp_grants`；收缩接口也会拒绝临时授权，避免“今天收缩、明天到期”的歧义。

## C. API 与鉴权

### C1. 业务失败却返回 HTTP 500/400 不统一

**现象**：前端拦截器需要在不同位置判断 `response.code` 与 HTTP 状态。

**处理**：`ApiError` 默认 HTTP 200 + `code!=200`；仅鉴权类显式传 `status_code`（401/429）。详见《参数说明.md》〇.3。

### C2. 身份不能读前端传的 user_id

**约定**：所有需要当前用户的接口用 `Depends(get_current_user)`；服务层只接收已认证的 `user` / `operator` 对象。

**反例**：从 query/body 读 `user_id` 再拼 SQL，会允许越权。

### C3. 中文查询参数在 curl 中未编码

**现象**：`curl ".../admin/users?keyword=李四"` 返回空或解析失败。

**原因**：URL 未做 percent-encoding。

**处理**：测试脚本改用 `--data-urlencode` 或直接取全量列表筛 ID；这是测试侧问题，不是接口缺陷。

### C4. 维护模式只拦非超管

**约定**：`maintenance_mode=true` 时普通用户与管理员登录返回 503，超级管理员仍可进入处理配置。

## D. Redis 与限流

### D1. Redis 不可用时不能“放行”

**处理**：`RateLimiter` 在 Redis 异常时降级为进程内滑动窗口，仍按同样阈值限制；不是关闭限流。

### D2. Redis 客户端连接可能拖慢启动

**处理**：先 1 秒 TCP 探活，再 `PING`（3 秒超时）；探活结论缓存 60 秒。不可用时 lifespan 打印 warning 后继续启动。

**依据**：`utils/redis_util.py`。

### D3. 登录成功会清空限流桶

**原因**：登录键是“账号+IP”，成功登录后清空，避免正常用户被之前的失败尝试误锁；失败尝试仍会累计。

### D4. 本机 Redis 无密码 / 有密码都能连

**现象**：`redis-cli -a 990108` 提示未配置密码，但带密码的 redis-py 仍可 `PING`。

**处理**：客户端支持 `REDIS_PASSWORD` 为空；部署时按实际 Redis 配置填写，不依赖该现象。

## E. 工程与重构

### E1. 目录重构后 `run.py` 仍引用旧路径

**现象**：热重载子进程报 `ModuleNotFoundError: No module named 'app.config'`。

**原因**：`run.py` 没有跟着 `app/config.py → app/core/config.py` 迁移。

**处理**：重构时全仓搜索旧模块名（`app.api`、`app.config`、`*_service`），并实际重启验证，不能只看 `compileall`。

### E2. `compileall` 查不出参数错误

**现象**：字典化改造后编译通过，但运行时报 `KeyError` / `TypeError`。

**处理**：每次重构后跑真实接口冒烟，至少覆盖登录、用户、配置、权限、运行状态五类。

### E3. 服务层与依赖层循环导入

**风险**：`core.deps → services.permissions.evaluate → core.deps.ApiError`。

**处理**：`require_permission` 内部延迟导入 evaluate；服务层只从 `core.deps` 导入 `ApiError` / `user_public`，不在模块顶层互相导入业务服务。

### E4. `seed` 与配置定义重复维护

**处理**：配置项只在 `services/config/meta.py::CONFIG_DEFINITIONS` 登记，种子和接口都读这一份，避免两处漂移。

## F. 运行状态

### F1. 没有 GPU 时接口不能报错

**处理**：`nvidia-smi` 不存在、超时或返回非 0 时返回空数组；前端展示“未检测到可用 GPU”。

### F2. `psutil.net_connections` 可能因权限失败

**处理**：用 `_safe` 包裹，失败时连接数为 0，不影响其余指标。

### F3. 状态采集不能阻塞事件循环

**处理**：CPU/磁盘/GPU/进程采集通过 `asyncio.to_thread` 执行，避免 `nvidia-smi` 或磁盘枚举卡住请求。
