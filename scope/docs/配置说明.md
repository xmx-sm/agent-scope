# scope/config — 默认配置中心（SQLite 存储）

`scope/config/` 是**基础设施层**（与 `scope/tools/` 平级，不是工具域）。它把散落在各域源码里的
硬编码默认值收敛到一处 `config.db`（SQLite），运行时按 **调用传入 > config.db > None** 读取。

用户 2026-11-22 决策：**全部默认值进 sqlite**，并**去掉 mail 的环境变量兜底**（默认值只此一个来源）。

---

## 一、读取优先级

```
调用传入 data  >  config.db（sqlite）  >  None / 出厂兜底
```

- 取到 `None` 时**由各函数原有逻辑决定报错还是回落**，config 层不加额外防御（用户明确要求）。
  例：`db.host` 出厂 None → `_resolve` 仍报「缺少数据库连接配置（db_config.host）」，文案不变。
- 敏感项（密码/账号）出厂 None，部署方手动写库注入后，调用链可**完全不传连接信息**。

三个文件：

| 文件 | 职责 |
|------|------|
| `schema.py` | 全部配置项的**单一真相源**（出厂默认 + 类型 + 说明 + 钳制/敏感标记）+ 导入即自检 |
| `store.py` | `config.db` 读写 + **进程级缓存**（同步读一次、之后 `get()` 走内存）+ 生命周期 API |
| `merge.py` | `pick` / `pick_str` / `pick_int` 三个合并辅助，处理 falsy 语义差异 |

---

## 二、为什么"同步读一次、之后走内存"

SQLite 是同步 IO，而工具链全异步。若每次 `get()` 都查库：① 阻塞事件循环（违反铁律 #8）
② 闸门在 `list_tables` 循环里逐表调用，IO 爆炸。

故 `load()` 一次性把全表读进进程级缓存 `_CACHE`，此后 `get()` 是纯内存操作（同步、无 IO）。
装配层启动时调一次 `await config.aload()`（同步 IO 放 `asyncio.to_thread`）。
未预载时首次 `get()` 惰性同步 load 一次（本地文件几十毫秒，可接受，但线上应显式预载）。

**库不存在时 `load()` 自动建库并灌出厂默认**——首次使用即 just works，无需单独建库步骤。

## 三、三类配置项的语义（关键）

73 项分三类，消费方式不同：

### ① 普通缺省项（57 项）—— 可自由调大调小

库里的值**直接生效**。如 `db.table_data.limit`、`mail.smtp.host`、`net.http_request.timeout`。

### ② 钳制项（10 项，🔒）—— 只收紧不放宽（铁律 #11）

这些是**服务端硬钳制上限**，消费点必须走 `store.clamp_get(key, hard_max)`：

```
clamp_get = min(sqlite值, hard_max)
  库设 2（收紧）  → 生效，返回 2
  库设 1000（放宽）→ 无效，被源码 hard_max 压回
  库为 null        → 回落 hard_max（出厂即上限）
  库是坏类型       → fail-safe 回落 hard_max（宁严不宁松）
```

`hard_max` 是**源码常量**，代表该能力的绝对上限，绝不因数据源松动。
若让它们被直接采信，部署方把 `crawl.semaphore_max` 调到 1000 就绕过了钳制——
这正是铁律 #11「能力只能收紧不能放宽」要防的。

| 钳制项 | hard_max | 含义 |
|--------|----------|------|
| `db.max_rows` | 500 | 查询行数硬上限 |
| `db.max_affect` | 100 | 写影响行数上限，超限回滚 |
| `db.list_tables.limit` | 200 | list_tables 条数上限 |
| `crawl.page_timeout_max` | 120000 | page_timeout 毫秒上限 |
| `crawl.semaphore_max` | 5 | 并发信号量上限 |
| `crawl.recycle_max` | 50 | 浏览器回收周期上限 |
| `crawl.batch_urls_max` | 20 | crawl_many 单次 URL 上限 |
| `crawl.deep_pages_max` | 30 | deep_crawl 总页数上限 |
| `crawl.links_limit` | 200 | links 每类条数上限 |
| `crawl.apply_wait_for.cap_ms` | 15000 | wait_for 轮询最长等待 |

### ③ 敏感项（6 项，🔑）—— 出厂 None，仅支持库注入

`db.host` / `db.user` / `db.password` / `db.database` / `mail.account.user` / `mail.account.password`。

- schema 里出厂值**强制 None**（导入自检会拦：敏感项出厂非 None 直接报错）
- 部署方 `config.set_value("db.password", "...")` 或 UPDATE 库注入
- `config.db` 已列入 `.gitignore`（`*.db`），**绝不入库**——密钥三不进

## 五、生命周期 API

```python
import scope.config as config

# 装配期（启动时一次）
config.configure("/etc/agent/config.db")   # 可选：改库路径，默认本目录 config.db
await config.aload()                        # 预载进内存缓存（同步 IO 进 to_thread，铁律 #8）

# 读（各域内部用，同步走缓存）
v = config.get("db.max_rows", 500)          # 普通项
v = config.clamp_get("db.max_affect", 100)  # 钳制项：min(sqlite, 100)，只收紧

# 写（部署/管理端）
config.set_value("mail.smtp.host", "smtp.163.com")   # 落库 + 更新缓存
config.set_value("db.password", "...")                # 敏感项注入
config.unset("db.max_rows")                            # 恢复出厂
config.init_db(reset=True)                             # 全库恢复出厂（会丢手动注入的敏感值！）

# 查
config.all_values()             # 全量快照 dict
config.schema_keys()            # 73 个 key
config.items_by_category("db")  # 某域的 Item 列表
config.describe("db.max_rows")  # 人类可读说明
```

`init_db()` 幂等：`INSERT OR IGNORE`，**不覆盖**部署方已改过的值。
`init_db(reset=True)` 才清空重灌——会丢手动注入的敏感值，仅用于恢复出厂。

## 六、三个合并辅助（`merge.py`，各域用这三个）

falsy 语义在不同字段上**相反**，故拆成三个，不能一刀切：

| 函数 | 传入 falsy 的处理 | 适用字段 |
|------|------------------|---------|
| `pick(passed, key, default)` | **0/False 算有效传入**，不被吞 | `verify`、`max_size`、`shell`、`save_attachments`、`output_limit` |
| `pick_str(passed, key, default="")` | 空串/空白算"未传"，继续找 sqlite，最后落 default | `host`、`encoding`、`mailbox`、`db_type`、`output_part` |
| `pick_int(passed, key, default)` | 空/None 去 sqlite；**0 的处理看具体字段** | 分页/截断类整数 |

**为什么必须分**：
- `verify=False` 是"关校验"的有效指令，若用 `or` 链会被吞成默认 True；
- `host=""` 必须落到空串让 `check_email_config` 报"缺少邮箱地址"，
  若把 None 变成字符串 `"None"` 就掩盖了错误。

**limit=0 特例**：`db.table_data.limit` / `db.run_query.limit` 用 `eff_*_limit()` getter，
内部对 0 回落缺省（0 行无意义，与原实现 `or 50` 一致）——与 `max_size=0`（0=不限，有意义）相反。
这两个 0 的语义不同，是分开的两个函数而非一个。

## 七、什么进 config、什么不进（边界）

**进**：带业务含义、部署方可按环境调整的缺省值（端口/主机/超时/上限/分页缺省/编码/开关）。

**不进（留源码常量）**——违反铁律 #11「能力只能收紧不能放宽」的风险项：

| 类别 | 例子 | 为何不进 |
|------|------|---------|
| 安全正则 | `_IDENT_RE`/`_READONLY_RE`/`_FORBIDDEN_RE`/`_FORBIDDEN_WRITE_RE` | 防 SQL 注入与越权写；放进库=把闸门钥匙交给数据源 |
| 系统目录名单 | `_TBL_CATALOGS`/`_SCHEMAISH` | 拒绝 information_schema/pg_catalog 可见 |
| 协议映射 | `_SQLGLOT_DIALECT`/`_SQLITE_EXTS` | 方言与扩展名是协议事实，非可调项 |
| function 白名单 | `FUNCTIONS`/`WRITE_FUNCTIONS` | 路由契约 |
| 进程级可变单例 | `_HTTP_CLIENT`/`_CRAWLER`/`_HOST_CTX`/`_START_LOCK` | 运行时状态，非配置 |
| 信封机器默认参 | `message="success"`/`func_name=""`/`code=400` | 函数签名，非配置 |
| 解析空值防御 | `data.get("url", "")` 里的空串 | "取不到即空"，非业务默认值 |

改这些是**显式的代码决策**，而非"调个配置"。

## 八、破坏性变更（平台侧须知）

### ① mail 环境变量兜底彻底移除

改造前 `get_email_config` 读 `os.environ`（`EMAIL_ADDR`/`EMAIL_PASSWORD`/`EMAIL_SMTP_HOST`/
`EMAIL_IMAP_HOST`/`EMAIL_SMTP_PORT`/`EMAIL_IMAP_PORT`）。改造后**全部删除**，默认值只此一个来源：config.db。

- 影响：今天靠 `EMAIL_*` 环境变量注入邮箱配置的部署，**必须改成写 config.db**
  （`config.set_value("mail.account.user", ...)` 或直接 UPDATE 库）。
- 实测确认：设了 `EMAIL_ADDR` 等环境变量，`get_email_config({})` 完全不读它们（返回空 host_user）。

### ② http_request / download 的 verify 传参语义

改造前调用方写 `data.get("verify", True)` 把缺省填成 True 传给 `get_http_client`，
导致 `get_http_client` 内部永远拿不到 None、sqlite 的 `net.verify=False` **永不生效**。
改造后调用方改传 `data.get("verify")`（无缺省），None 才落到 `_pick` 读 sqlite。

## 九、`.gitignore` 关系

`config.db` / `config.db-wal` / `config.db-shm` 命中 `.gitignore` 的 `*.db` 规则，**不入库**。
库文件是运行时产物（含部署方注入的敏感凭证），入库即泄密。

首次 `load()` 自动建库，故 clone 后无需任何 setup——但敏感项出厂 None，
要用 db/mail 的"零传参直连"能力需部署方自行 `set_value` 注入。
