本版本范围说明：

- “框架层搭建完成”指 AgentScope 核心能力、工具/配置/权限/RAG/中间件/工作区/
  记忆/实时语音与统一后端入口完成。
- HTTP / SSE / WebSocket、会话持久化、业务 session registry 按无状态设计由业务后端实现，
  不是本版本缺口。
- `storage/` 是可选内置存储层；业务后端已有数据库时不需要启用。

仍可按需补齐：

```
storage/       可选的框架内置会话持久化
permission/    前端审批 UI、Redis/Postgres pending、完整引擎级审计
main.py        HTTP/SSE/WebSocket 服务入口（业务后端实现）
```

对比 `agent_study/scope`，剩下的不是单点能力，而是服务化链路：

```
模型 → Agent → 工具装配 → 运行循环 → 审批 → 记忆 → RAG → 服务化
```

接下来优先做 **storage / 服务化入口**。

## 三-B、模型工厂（已实现）

代码：

```
scope/llm/
├── agent_model.py  # 对外入口：Chat / Embedding / TTS / ASR / 能力描述
├── _factory.py     # 内部：provider 注册表、凭证、参数过滤、构造器
├── formatters.py   # 视频输入 formatter
└── __init__.py
```

### 入口

```python
from scope.llm import (
    async_get_llm_model,
    async_get_embedding_model,
    async_get_tts_model,
    async_get_asr_model,
    get_model_capabilities,
)

r = await async_get_llm_model({
    "llm": {
        "provider": "openai-compatible",
        "model": "gpt-4o",
        "api_key": "...",
        "base_url": "https://api.example.com/v1",
        "stream": True,
        "think": False,
        "context_size": 128000,
    }
})
# r = {"code": 200, "data": <ChatModel>, "message": "模型初始化成功"}
```

### 已支持 provider

| 类型 | provider |
|---|---|
| Chat | `openai`（Responses）、`openai-chat` / `openai-compatible`、`anthropic`、`dashscope` / `qwen`、`deepseek`、`gemini`、`moonshot` / `kimi`、`xai` / `grok`、`ollama`、`minimax`、`volcengine` / `doubao` |
| Embedding | `openai`、`openai-chat`、`dashscope`、`gemini`、`ollama` |
| TTS | `openai`、`dashscope`（standard/cosyvoice/realtime）、`gemini`、`minimax` |
| ASR | `openai`、`dashscope`（standard/realtime） |

### 设计边界

工厂只做四件事：

1. provider → 模型类 / 凭证类 / formatter 类映射；
2. 按目标类 `__init__` 签名过滤参数；
3. 按 `Parameters.model_fields` 过滤模型参数；
4. 把缺失的可选 SDK 转成 400 + pip 安装指引。

不做：业务逻辑、Message/DataBlock 构造、附件读取、密钥管理、自动选模型。

### 多模态设计

**需要设计，但只做“接线”，不做附件处理。**

| 层 | 职责 |
|---|---|
| 模型工厂 | 声明/配置 `input_types`，选择支持视频的 formatter |
| 消息层 | 构造 `TextBlock` / `DataBlock`，图片/音频/视频源用 `URLSource` 或 `Base64Source` |
| 附件层 | 文件读取、大小限制、base64 转换、租户校验 |
| Agent runtime | 把 Msg 交给模型，把 `DataBlockStart/Delta/End` 事件推给前端 |

支持矩阵：

| provider | text | image | audio | video | pdf |
|---|---:|---:|---:|---:|---:|
| `openai-chat` / `openai-compatible` | ✅ | ✅ | ✅ | ✅ 需 `video_support=True` | ✅ |
| `dashscope` | ✅ | ✅ | ✅ | ✅ 需 `video_support=True` | — |
| `gemini` | ✅ | ✅ | ✅ | ✅ 默认支持 | ✅ |
| `anthropic` | ✅ | ✅ | — | — | ✅ |
| `openai`（Responses） | ✅ | ✅ | — | — | ✅ |
| 其余 | ✅ | 视模型 | 视模型 | — | — |

视频注意事项：

- 必须显式 `video_support=True`；否则默认 formatter 会跳过 `video/*`。
- `openai-chat` / `openai-compatible` 使用 `OpenAIVideoChatFormatter`；
- `dashscope` 使用 `DashScopeVideoChatFormatter`（支持 `video_fps` 默认值）；
- `gemini` 默认 formatter 已支持视频，不需要自定义；
- 其他 provider 配 `video_support=True` 直接返回 400，不静默忽略。
- 视频块格式固定为 `{"type":"video_url","video_url":{"url":...}}`，不要用 `{"type":"video"}`。

## 三-C、媒体生成服务（已实现）

代码：

```
scope/media/
├── tts.py      # 文本 → 音频 → 文件 / base64 / URL

├── fs.py       # 读/写文件闸门
```

### 分工

| 层 | 职责 |
|---|---|
| `llm.agent_model` | 只构造可复用的模型对象 |
| `media.tts` / `media.asr` | 字典入参、输出位置校验、流式拼接、原子落盘 |

### TTS

```python
from scope.media import async_generate_tts

r = await async_generate_tts({
    "tts": {
        "provider": "dashscope",
        "model": "qwen3-tts-flash",
        "api_key": "...",
        "parameters": {"voice": "Cherry"},
    },
    "text": "你好，这是一段测试语音",
    "output_mode": "file",          # file / base64 / url
    "save_path": "/data/audio/hello.mp3",
    "overwrite": False,
})
# 200: {"path", "bytes", "media_type"}
# 400: 缺少 save_path / 路径被拒 / 文件已存在 / PCM 非 .wav ...
```

规则：

- `output_mode=file` 时 **`save_path` 必填**，缺了直接 400；
- `output_mode=base64` 不需要路径；
- `output_mode=url` 只对返回 URL 的厂商有效；
- 流式 TTS 会把增量 chunk 拼成完整音频；
- `audio/pcm` 且保存为 `.wav` 时自动补 WAV header；
- 写入使用临时文件 + `os.replace` 原子落盘。

### ASR

```python
from scope.media import async_transcribe_asr

r = await async_transcribe_asr({
    "asr": {"provider": "openai", "model": "gpt-4o-mini-transcribe", "api_key": "..."},

```

### 文件闸门

```python
from scope.media.fs import configure_fs_policy

configure_fs_policy({
    "allowed_roots": ["/data/audio", "/data/text"],
    # 或注入平台回调 check_write(path) -> (bool, reason)
    # "check_write": my_check_write,
})
```

- 未注入时只允许当前工作目录子树；
- 绝对路径 + 拒绝 `..`；
- 读写都走闸门；
- 生成服务不直接 `open` 任意路径。

### 多后端配置

每个后端使用独立配置段，选择类参数缺失直接 400。

#### Zvec（本地）

```python
{
    "rag_config": {
        "type": "zvec",
        "zvec_config": {
            "path": "/data/tenants/u1/zvec",
            "create_dir": True,
            "collection": "handbook",
            "mode": "hybrid",          # embedding / bm25 / hybrid
            "metric_type": "cosine",
            "fts_tokenizer": "jieba",
            "fts_filters": ["lowercase"],
        },
    },
}
```

- `mode=embedding`：只需 embedding，不需要文本索引
- `mode=bm25`：不需要 embedding；实体检索走 BM25
- `mode=hybrid`：向量 + BM25，使用 RRF 融合
- `path` 必填绝对路径；建议每个租户一个目录
- 依赖：`pip install zvec`

#### Qdrant

```python
{
    "type": "qdrant",
    "qdrant_config": {
        "path": "/data/tenants/u1/qdrant",  # 本地磁盘；也可用 url
        "url": None,
        "api_key": None,
        "distance": "Cosine",
        "client_kwargs": {},
    },
}
```

- `location=":memory:"` 用于临时内存
- 远程：`url` + `api_key`
- 依赖：`pip install qdrant-client`

#### Milvus

### 官方 KnowledgeBase / RAGMiddleware（多后端）

各后端都实现了 `agentscope.rag.VectorStoreBase`，因此可以直接构建官方
`KnowledgeBase` 与 `RAGMiddleware`：

```python
from scope.rag import async_create_rag_middleware

r = await async_create_rag_middleware({
    "knowledge_bases": [
        {
            "name": "handbook",
            "description": "公司制度与流程",
            "collection": "handbook",
            "sqlite_config": {"base_dir": "/data/rag_db"},
            "metadata_filter": {"tenant_id": "t1"},
            "embedding": {"provider": "openai", "model": "...", "api_key": "..."},
        }
    ],
    "search_config": {"mode": "agentic", "top_k": 5},
    "rerank_model": {
        "provider": "dashscope",
        "model": "qwen-max",
        "api_key": "...",
    },
})
mw = r["data"]["middleware"]

agent = Agent(..., middlewares=[mw])
```

- `mode="agentic"`：暴露 `search_knowledge` 工具，由模型决定何时检索；
- `mode="static"`：每轮用户输入自动检索并注入 HintBlock；
- `rerank_model` 支持模型对象或字典，字典走 `scope.llm`；
- `metadata_filter` 由各向量库适配器在 search/list/delete 时强制过滤；
- embedding 可全局传 `embedding` / `embedding_model`，也可每个 KB 覆盖；
- 每个 KB 通过 `type` + `<backend>_config` 选择后端；Zvec `mode=bm25` 不需要 embedding；
- 写入仍走 `KnowledgeBase.insert_document(chunks)` 或 `async_rag_tools(function="write")`。

> Agentic 模式下 `search_knowledge` 是中间件 `list_tools()` 贡献的工具。
> 使用 `async_get_agent` 时需加 `"middleware_tools": {"enabled": True}`，
> 框架才会把它加入 Toolkit。

### 设计说明

- **参数优先级**：`data > config.db > 代码默认 / 400`
  - `rag.type` / `rag.sqlite.path` / `rag.sqlite.base_dir` 缺则 400
  - `rag.sqlite.create_dir` / 顶层 `create_dir` 控制目录不存在时是否自动创建
  - `rag.top_k` / `rag.chunk_size` / `rag.overlap` / `rag.require_file` 未传时读 config.db，再回落代码默认
  - `rag.embedding.*` 在 `data["embedding"]` 未传时补齐
- **动态存储位置**：`sqlite_config.base_dir` 可由用户/租户按请求传入，适合 SaaS 多租户；
  目录不存在默认 400，传 `create_dir=True` 才创建。
- **文件读取闸门**：RAG 解析前调用 `scope.common.fs.check_read_path`，未配置时只允许 cwd 子树，可注入 `allowed_roots` / `check_read`。
- **文档管理**：`documents` 按 doc_id 聚合返回文档列表；`delete` 仍按 doc_id 删除。
- **默认 `require_file=True`**：路径写错直接 400，避免把路径字符串当正文入库。
- **写入幂等**：同一 `doc_id` 重写时先删旧 chunk，再插入新 chunk。
- **维度校验**：检索前校验 query 维度与集合维度一致，不一致直接 400。
- **后端口径**：`sqlite` 仅支持 dense；sparse/hybrid 后续由其他后端提供。
- **与官方 RAGMiddleware 的关系**：本层先提供“可用的知识库 + 工具”；
  后续接 `RAGMiddleware` 时，可直接复用本层的 parser/chunker/registry，
  检索入口替换成官方 `KnowledgeBase`。

### 工具权限 / 工具组

子智能体默认**不会继承主 Agent 的完整 Toolkit**。构建顺序：

```text
spec.toolkit（显式完整 Toolkit）
  > spec.tools / spec.tool_groups
  > data.toolkit（仅直接调用 async_run_subagent 时）
  > 空 Toolkit
```

`tool_groups` 支持三种写法：

```python
# 1. 从父 Toolkit 选组
"tool_groups": ["rag", "net"]

# 2. 直接定义组：组名 -> 工具列表
"tool_groups": {
    "rag": ["async_rag_tools"],
    "net": ["async_req_tools"],
}

# 3. 完整组定义
"tool_groups": [
    {
        "name": "rag",
        "description": "知识库检索",
        "instructions": "按 function 选择操作",
        "tools": ["async_rag_tools"],
    }
]
```

过滤：

```python
"allow_tools": ["async_rag_tools"],   # 只保留这些工具名
"deny_tools": ["async_sys_tools"],    # 排除这些工具名
"allowed_tools": [...],               # allow_tools 别名
"denied_tools": [...],                # deny_tools 别名
```

规则：

- `tools` 与 `tool_groups` 可以同时存在：`tools` 进 basic 组，`tool_groups` 进独立组；
- `allow_tools` 同时作用于 `tools` 与组内工具；
- `deny_tools` 优先级高于 allow；
- `spec.toolkit` 是完整 Toolkit，传入后不再自动过滤；
- 委派工具只把主 Toolkit 作为 `parent_toolkit` 用于“选组”，不会直接共享给子智能体。

### 工具审批（组级 / 工具级）

除了“给哪些工具”，还可以配置“哪些调用需要审批”：

```python
spec = {
    "tool_groups": ["rag", "sys"],
    "tool_approval": {
        "rag": "allow",             # 组级：直接放行
        "sys": "ask",               # 组级：需要审批
        "async_db_write_tools": "deny",  # 工具级：覆盖组级
        "default": "allow",
    },
}
```

取值：

| 值 | 行为 |
|---|---|
| `allow` | 自动确认 |
| `deny` | 自动拒绝 |
| `ask` | 调 `approval_handler`；没有 handler 则 fail-closed 拒绝 |

优先级：

```text
工具名 > 组名 > default
```

审批回调：

```python
async def my_approval(tool_call, group, decision) -> bool | dict:
    # 可推送到前端 / 企业 IM / 人工审批队列
    return True

await async_run_subagent({
    "subagent": "coder",
    "task": "...",
    "subagents": [spec],
    "approval_handler": my_approval,
})
```

注册时注入：

```python
await register_delegate_tool(
    tk, subagents=[spec], approval_handler=my_approval)
```

#### 主智能体代替用户审批

显式开启：

```python
spec["approval"] = {"mode": "main_agent"}
# 或
spec["main_agent_approval"] = True
```

注册时把主 Agent 传进来：

```python
await register_delegate_tool(
    tk,
    subagents=[spec],
    main_agent=main_agent,
    approval_mode="main_agent",
)
```

行为：

- 用主 Agent 的 **model** 创建一个无工具的审批 Agent；
- prompt 固定为“判断工具调用是否允许”，只允许回答 `ALLOW` / `DENY`；
- 默认拒绝，只有明确 `ALLOW` 才放行；
- 工具参数被标注为不可信内容，避免参数里的指令影响审批；
- 不把主 Agent 的 Toolkit 给审批 Agent，避免递归调用委派工具。

优先级：

```text
显式 approval_handler
  > approval.mode = main_agent
  > approval.mode = deny
  > approval.mode = user（无 handler 时 ask 拒绝）
```

⚠️ 安全提示：主智能体审批本质是“模型审批模型”，存在自授权和
prompt injection 风险。高危险工具组建议仍走用户/管理员审批，或使用
独立的审批 Agent + 人工兜底。

说明：

- 没有 `approval_handler` 时，`ask` 按拒绝处理（安全默认）。
- 后台任务同样走该策略；后台模式没有人可问时，`ask` 会拒绝。
- `ToolGroup` 的激活工具 `reset_tools` 本身在 AgentScope 中恒放行；
  审批发生在具体工具调用时。
- `permission_context` 仍然可以控制引擎模式；`tool_approval` 是子智能体层的
  组级/工具级策略，两者可叠加。

### 当前限制

- 子智能体支持 `tool_approval`（allow/deny/ask）；`ask` 需要 `approval_handler`；
  没有 handler 时按拒绝处理。真正的前端/IM 审批 UI 仍需后续接 `permission/`
- 后台任务无人可问时，`ask` 会拒绝；需要预授权或接审批队列
- 后台任务仅单进程
- 主 Agent `builder` / `runtime` / 上下文管理已实现；`Toolkit` 装配层仍需按业务补齐
- 中断：挂起确认走 `UserInterruptEvent`，活跃生成走 task cancel；
  完整前端 UI / SSE 仍需业务层接
- A2A 暂不做

## 三-F、主 Agent 运行时（已实现）

代码：`scope/agent/runtime.py`

```python
from scope.agent import AgentRuntime

runtime = AgentRuntime(
    agent,
    tool_approval={
        "sys": "ask",
        "db": "deny",
        "default": "allow",
    },
    approval_handler=my_handler,   # 可选
)

async for event in runtime.reply_stream(UserMsg(name="user", content="...")):
    if isinstance(event, RequireUserConfirmEvent):
        await ui.show_confirm(event)
    else:
        renderer.render(event)
```

### 工具审批

- `allow`：自动确认
- `deny`：自动拒绝
- `ask`：
  - 有 `approval_handler` → 回调
  - 无 handler → 产出 `RequireUserConfirmEvent`，等待调用方
- 优先级：工具名 > 工具组 > `default` > 构造参数 `default_approval`

调用方回填：

```python
runtime.resolve_confirm(
    reply_id=event.reply_id,
    decisions={"tool_call_id": True},
)
# 或
runtime.resolve_confirm(reply_id=event.reply_id, approved=True)
```

### 中断

```python
# 挂起确认时：回填中断
await runtime.interrupt(reply_id)

# 正在生成时：取消当前运行 task
await runtime.interrupt()
```

语义：

- 挂起确认：发送 `UserInterruptEvent`，Agent 关闭 pending tool calls
- 活跃生成：cancel 当前 `asyncio.Task`
- 空闲：返回 False

### 人机交互

- `RequireUserConfirmEvent` 可直接交给前端 / IM
- `pending_confirms()` 列出待确认事件（含官方生成的 `suggested_rules`）
- `resolve_confirm` 支持逐工具决定
- `resolve_confirm(..., accept_suggested_rules=True)` 会把接受调用的建议规则回传，后续相同调用不再询问
- `set_permission_mode("explore"/"bypass"/...)` 可在运行时切换官方权限模式
- `RequireExternalExecutionEvent` 由 runtime 调用本地 toolkit 执行

### 子智能体取消

- `async_cancel_subagent_task(task_id)`：取消后台任务
- `register_delegate_tool` 会注册 `subagent_task_cancel` 工具
- 前台执行可传 `cancel_event`（`asyncio.Event`）

## 三-H、流水线（已实现构建器）

代码：`scope/agent/pipeline.py`

支持两种官方流水线：

- `GoalPipeline`：执行者 + 验证者循环
- `TeamPipeline`：队长 + 成员，通过 `TeamAssign` 分派

### GoalPipeline

```python
from scope.agent import async_get_pipeline

r = await async_get_pipeline({
    "type": "goal",
    "executor": {
        "name": "Executor",
        "system_prompt": "你负责写代码",
        "tools": [...],
    },
    "verifier": {
        "name": "Verifier",
        "system_prompt": "你负责验收",
        "tools": [...],
    },
    "max_iters": 5,
    "max_retries": 3,
    "verifier_reset_context": True,
    "offload": {
        "enabled": True,
        "workdir": "/data/pipeline_workspace",
    },
})
pipe = r["data"]["pipeline"]

async for event in pipe.reply_stream(user_msg):
    ...
```

- 执行者与验证者共享同一个 offload/workspace，验证者才能看到执行者写出的文件
- 验证者通过结构化输出给出 `pass` / `fail` / `impossible`
- 未通过时 `message` 会带着理由退回执行者
- `max_iters` 控制驳回次数，`max_retries` 控制结构化输出重试

### TeamPipeline

```python
r = await async_get_pipeline({
    "type": "team",
    "leader": {
        "name": "Leader",
        "system_prompt": "你负责拆解与分派",
    },
    "members": [
        {
            "agent": {
                "name": "Researcher",
                "system_prompt": "你负责检索",
                "tools": ["async_rag_tools"],
            },
            "description": "负责检索资料",
        },
        {
            "agent": {
                "name": "Coder",
                "system_prompt": "你负责写代码",
                "tools": ["async_sys_tools"],
            },
            "description": "负责写代码",
        },
    ],
    "reset_members": True,
})
pipe = r["data"]["pipeline"]
```

- 队长拿到 `TeamAssign(member, prompt)` 工具
- 成员只把最终回复交回队长，中间过程不进队长上下文
- 同一轮不同成员并发，同一成员按调用顺序串行
- `reset_members` 控制队长每轮结束后是否清空成员上下文

### 人机交互

流水线遵循 `PipelineProtocol`：

```text
pipe.reply_stream(Msg)                    # 开始
pipe.reply_stream(UserConfirmResultEvent) # 恢复工具授权
pipe.reply_stream(ExternalExecutionResultEvent)
pipe.reply_stream(UserInterruptEvent)     # 中断整条流水线
```

- 任一 Agent 停在工具授权时，事件流结束
- 用户答复按 `reply_id` 送回对应 Agent
- 流水线的 `reply_stream` 替代单 Agent runtime

### 与子智能体的区别

| 方式 | 编排 |
|---|---|
| 子智能体 delegate | 主 Agent 决定何时调用哪个子智能体 |
| GoalPipeline | 执行者/验证者固定循环 |
| TeamPipeline | 队长动态分派给成员，成员结果作为工具结果 |

## 三-I、SOP 标准作业流程（已实现构建器）

代码：`scope/agent/sop.py`

SOP 是固定顺序的里程碑列表：每个步骤由执行者完成、验证者验收，通过后才进入下一步。
与 `GoalPipeline` 的区别：

| 方式 | 结构 |
|---|---|
| `GoalPipeline` | 一个执行者 + 一个验证者，反复重做同一目标 |
| `SOP` | 多个步骤按顺序推进，每个步骤独立验收与重试 |

### 构建

```python
from scope.agent import async_get_sop

r = await async_get_sop({
    "sop": {
        "name": "write-article",
        "description": "写一篇可发布的技术文章",
        "steps": [
            {
                "subject": "列大纲",
                "description": "至少三个章节，每章一句摘要",
                "executor": {
                    "name": "Outliner",
                    "system_prompt": "你负责列大纲",
                },
                "max_attempts": 3,
            },
            {
                "subject": "写正文",
                "description": "按大纲写完，落盘到 article.md",
                "executor": {
                    "name": "Writer",
                    "system_prompt": "你负责写正文",
                    "tools": ["async_sys_tools"],
                },
                "verifier": {
                    "name": "Editor",
                    "system_prompt": "你负责验收正文",
                    "tools": ["async_sys_tools"],
                },
                "max_attempts": 3,
            },
        ],
    },
    "offload": {
        "enabled": True,
        "workdir": "/data/sop_workspace",
    },
})
sop = r["data"]["sop"]
engine = r["data"]["engine"]

async for event in engine.reply_stream(user_msg):
    ...
```

- 每个步骤必须提供 `subject`、`description`、`executor`
- `verifier` 可选；不提供时执行者交出内容即视为通过
- `max_attempts` 由引擎控制，默认 `3`
- 执行者把结果写成 `handover`，下一步只能看到这段交接文本，看不到上一步的文件、工具输出或对话
- 需要跨步骤共享文件时，在顶层传 `offload` / `workspace`，所有步骤共用同一个 `LocalWorkspace`
- 同一个执行者对象可以在多个步骤复用，从而共享上下文；用字典配置时每个步骤会新建 Agent

### 运行状态持久化

```python
from scope.agent import save_sop_state, load_sop_state

json_text = await save_sop_state(engine)
# 存库 / 存文件

state = await load_sop_state(json_text)
r = await async_get_sop({
    "sop": {...同一定义...},
    "state": state,
})
engine = r["data"]["engine"]
```

- `SOPRunState` 是纯数据，可持久化后在新进程恢复
- 恢复时必须使用**步骤数量相同**的 SOP，否则返回 400
- 恢复只还原 SOP 状态；执行者/验证者自身的 Agent 状态需要调用方先恢复
- 新运行不要传 `state`；同一 SOP 定义可以被多次运行复用

### 人机交互

`SOPEngine` 与 Agent 一样实现 `reply_stream`：

```text
engine.reply_stream(Msg)                    # 开始
engine.reply_stream(UserConfirmResultEvent) # 恢复工具授权
engine.reply_stream(ExternalExecutionResultEvent)
engine.reply_stream(UserInterruptEvent)     # 中断
```

- 任一步骤停在工具授权时事件流结束，不会挂起进程
- 答复送回挂起的那一步
- 中断当前步骤不会消耗重试次数，步骤回到 `PENDING`

## 三-J、权限系统（已实现字典构建器）

代码：`scope/permission/`

直接用官方 `agentscope.permission`，不复制规则匹配、只读判定或危险路径检查：

- `PermissionMode`：全局策略
- `PermissionRule`：allow / deny / ask 规则
- `PermissionContext`：模式 + 规则 + 工作目录
- `PermissionEngine`：Agent 内部按规则和工具检查给出 ALLOW / DENY / ASK

本层只负责把业务字典翻译成 `PermissionContext`，并在运行时提供模式切换和建议规则回传。

### 模式

| 模式 | 行为 |
|---|---|
| `default` | 默认询问，只读调用和命中 allow 规则时放行 |
| `accept_edits` | 工作目录内编辑自动放行，其余按规则 |
| `explore` | 只读模式，修改类调用直接拒绝 |
| `bypass` | 跳过安全检查，只保留显式 deny / ask 规则；高风险场景慎用 |
| `dont_ask` | 所有 ASK 转 DENY，适合无人值守任务 |

### 字典配置

推荐使用顶层 `permission` 字典；旧的 `permission_context` 仍兼容。

```python
{
    "permission": {
        "enabled": True,              # 总开关；False 时全部关闭，走官方默认
        "mode": "default",
        "source": "projectSettings",
        "allow": {
            "Bash": ["git status:*", "npm run:*"],
            "async_db_tools": ["run_query"],
        },
        "deny": {
            "Bash": ["rm:*"],
            "Write": ["**/.ssh/**"],
        },
        "ask": {
            "async_sys_tools": [None],
        },
        "working_directories": [
            "/data/project",
            {"path": "/data/shared", "source": "session"},
        ],

        # 以下能力默认关闭，必须显式开启
        "sqlite": {
            "enabled": False,
            "path": "/data/tenants/u1/permission.db",
            "create_dir": True,
            "tenant_id": "u1",
            "agent_id": "a1",
        },
        "audit": {
            "enabled": False,
        },
        "pending": {
            "enabled": False,
            "ttl_seconds": 300,
        },
        "function_rules": {
            "enabled": True,
        },
    },
}
```

开关约定：

| 配置 | 默认 | 开启后 |
|---|---|---|
| `permission.enabled` | `True` | `False` 时忽略所有子项，使用官方默认 `PermissionContext` |
| `sqlite.enabled` | `False` | 创建/读取 SQLite，合并持久化规则 |
| `audit.enabled` | `False` | 确认结果写入审计表；必须同时开 `sqlite` |
| `pending.enabled` | `False` | 待确认事件写入共享表；必须同时开 `sqlite` |
| `function_rules.enabled` | `False` | 子智能体工具按 `data["function"]` 细分规则；默认不包装 |


也兼容官方形状：

```python
{
    "mode": "dont_ask",
    "allow_rules": {
        "Bash": [
            {
                "tool_name": "Bash",
                "rule_content": "git commit:*",
                "source": "projectSettings",
            },
        ],
    },
}
```

以及逐条规则列表：

```python
{
    "mode": "default",
    "rules": [
        {
            "tool_name": "Bash",
            "rule_content": "npm run:*",
            "behavior": "allow",
            "source": "projectSettings",
        },
    ],
}
```

约定：

- `allow` / `deny` / `ask` 键是工具名
- 值可以是字符串、`None`、字典或列表
- `None` 表示工具名级规则，匹配该工具的所有调用
- 字符串表示 `rule_content`
- `source` 缺省为 `projectSettings`
- `working_directories` 必须是绝对路径

### 自定义工具：按 `data["function"]` 细分

官方 `FunctionTool` / MCPTool 不重写 `match_rule`，默认只能按工具名控制：

```python
{"allow": {"async_db_tools": [None]}}
```

本项目新增 `PermissionedFunctionTool`，把 `data["function"]` 纳入规则：

```python
{
    "allow": {"async_db_tools": ["run_query", "list_tables"]},
    "deny":  {"async_db_tools": ["run_sql"]},
}
```

匹配语义：

| `rule_content` | 含义 |
|---|---|
| `None` / `"*"` | 整个工具 |
| `"run_query"` | 精确匹配 function |
| `"run_*"` / `"run_query:*"` | 前缀匹配 |
| `"*query"` | 后缀匹配 |

子智能体工具只有在 `permission.function_rules.enabled=True` 时才包装成
`PermissionedFunctionTool`；默认不包装，保持官方工具名级规则。
主 Agent 如果直接传入 `Toolkit`，可用：

```python
from scope.permission import wrap_permissioned_tools

tk = Toolkit(tools=wrap_permissioned_tools([async_db_tools]))
```

未包装的普通 `FunctionTool` 仍按官方工具名级语义处理。

### 分布式 pending confirm

开启方式同样在字典里：

```python
{
    "permission": {
        "pending": {"enabled": True, "ttl_seconds": 300},
        "sqlite": {
            "enabled": True,
            "path": "/data/tenants/u1/permission.db",
            "tenant_id": "u1",
            "agent_id": "a1",
        },
    },
}
```

同一个 `PermissionStore` 保存待确认事件，支持多 worker 轮询：

```python
runtime = AgentRuntime(agent)

# worker A：事件流挂起时写入 pending
async for event in runtime.reply_stream(msg):
    ...

# worker B / UI：读取跨进程待确认
items = await runtime.pending_store.list_pending(
    tenant_id="u1", status="pending")
await runtime.pending_store.resolve_pending(key, {"approved": True})

# 或同一 runtime
await runtime.resolve_confirm_async(reply_id, approved=True)
```

语义：

- `pending_confirms()` 仍是进程内视图
- `list_pending_confirms()` 配置了 `pending_store` 时读共享表
- `resolve_confirm_async()` 确保结果先落库
- 超时未确认按拒绝处理
- SQLite WAL 适合中小规模；高并发/多实例建议换 Redis/Postgres 实现同一接口

### 运行时

```python
from scope.agent import AgentRuntime

runtime = AgentRuntime(agent)

# 运行时切换模式
runtime.set_permission_mode("dont_ask")

# 待确认事件
for item in runtime.pending_confirms():
    item["tool_calls"][0]["suggested_rules"]

# 接受建议规则
runtime.resolve_confirm(
    reply_id,
    approved=True,
    accept_suggested_rules=True,
)
```

- `pending_confirms()` 现在带 `suggested_rules`
- `resolve_confirm(..., accept_suggested_rules=True)` 会把被接受调用的建议规则放进 `ConfirmResult.rules`
- 规则由官方 Agent 自动写入权限引擎，后续相同调用不再询问
- 安全 ASK（`bypass_immune`）不会被 allow 规则覆盖
- 审计与共享 pending 需要显式传 `audit_store` / `pending_store`

### 与 `tool_approval` 的关系

| 机制 | 层级 | 用途 |
|---|---|---|
| `permission_context` | 官方权限引擎 | 推荐方式：模式 + 规则 + 工具检查 |
| `tool_approval` | `AgentRuntime` / 子智能体包装层 | 兼容旧调用：对已出现的确认事件做 allow / deny / ask 决策 |

新代码优先使用 `permission_context`。`tool_approval` 的 `allow` 是对事件层的直接放行，不会经过官方安全检查，生产环境不要用它兜底放行所有工具。

## 四、工具审批设计

> 4.1 的 `PermissionContext` 字典构建、模式切换、SQLite 规则/审计/pending 与
> `PermissionedFunctionTool` 已落地（见三-J）；本节余下内容是前端审批 UI
> 与更完整权限引擎审计的规划。

### 4.1 不自造引擎，使用 agentscope 2.0.12 现成能力

已安装的 `agentscope.permission` 提供：

- `PermissionContext`：`mode` + allow/deny/ask 规则 + 工作目录
- `PermissionRule`：`tool_name` / `rule_content` / `behavior` / `source`
- `PermissionEngine`：按模式判定 ALLOW / DENY / ASK
- `PermissionMode`：DEFAULT / EXPLORE / ACCEPT_EDITS / BYPASS / DONT_ASK
- `Agent` 内部已经 `PermissionEngine(state.permission_context)`
- 判定为 ASK 时，Agent 会发 `RequireUserConfirmEvent`，回 `UserConfirmResultEvent` 即可

审批层要做的是：

1. **规则持久化**（谁、对哪个 Agent、哪个工具、允许/拒绝/询问）
2. **运行时确认**（前端卡片、等待用户选择）
3. **审计**（谁在何时批准了什么）
4. **非交互策略**（定时任务/机器人后台自动拒绝）

> 1、3、4 的基础实现已落地（PermissionStore + DONT_ASK）；2 的运行时事件已通，
> 前端审批卡片仍需业务侧实现。

不重写权限引擎。

### 4.2 审批粒度：最容易踩的坑

agentscope 的 `FunctionTool` / MCPTool **不重写 `match_rule`**，因此原生只能做到工具名级审批。

本项目已实现 `scope/permission/tool.py::PermissionedFunctionTool`：

- `rule_content=None`：整个工具
- `rule_content="run_query"`：按 `data["function"]` 精确匹配
- `rule_content="run_*"` / `"run_query:*"`：前缀匹配
- `rule_content="*query"`：后缀匹配

子智能体工具需要在 `permission.function_rules.enabled=True` 时才会在
`normalize_tools` 中自动包装；主 Agent 可用 `wrap_permissioned_tools([...])` 手动包装。

仍然限制：

- 只对 `PermissionedFunctionTool` 生效
- MCP 工具仍按官方工具名级规则
- `async_email_tools` 等工具必须通过包装器注册后，才能区分 `send_email` / `receive_email`

### 4.3 默认策略建议

| 工具 | 默认 | 原因 |
|---|---|---|
| `Read` / `Glob` / `Grep` / `async_db_tools` / `async_rag_tools` 的 read | ALLOW | 只读 |
| `async_db_write_tools` | ASK | 数据变更 |
| `async_sys_tools` / `Bash` | ASK（生产建议 DENY + 白名单） | 命令执行 |
| `async_email_tools` 的 `send_email` | ASK | 对外发信 |
| `net.download` / `screenshot` / `crawl` 写文件 | ASK | 落盘 |
| MCP 工具 | 默认 ASK，按 server 配置 | 第三方能力不可信 |
| `async_db_tools` 的 `run_query` | 视情况 ASK | 可读全库 |

### 4.4 交互与非交互

- **交互式**（网页/IM）：
  `RequireUserConfirmEvent` → 前端卡片 → 用户选“允许一次 / 本会话允许 / 永久允许 / 拒绝” → 回 `UserConfirmResultEvent`。
- **非交互式**（定时任务/机器人后台）：
  `PermissionMode.DONT_ASK`，ASK 直接转 DENY；绝不能默认放行。
- **记住选择**：
  一次/会话规则放 `AgentState.permission_context`；永久规则落 SQLite。
- **多 worker**：
  进程内 pending map 只适合单 worker；分布式必须用 Redis/DB + 锁，或走 `agentscope.app` 的会话/消息总线。

### 4.5 审批前必须先处理 B3

已有缺陷 **B3**：工具返回 `{"code":400}`，agentscope 侧仍记为 `state=success`。  
审批层如果靠工具返回值判断成功/失败会被误导。建议：

- 工具返回 `ToolChunk(state=ERROR)`，或在包装器里把 `code != 200` 转成错误结果；
- 审批审计只看 **permission decision + 工具结果状态**，不看业务 `code`。

## 五、RAG 设计

### 5.1 优先用官方 `agentscope.rag`

agentscope 2.0.12 已自带：

- `KnowledgeBase`：一个知识库 = embedding 模型 + vector store + collection + `metadata_filter`
- 解析器：Text / PDF / PPT / Word / Excel / Image
- 切块：`ApproxTokenChunker`
- 向量库：MilvusLite / Qdrant / MongoDB / Elasticsearch
- `RAGMiddleware`：`agentic`（给模型一个 `search_knowledge` 工具）/ `static`（每轮自动检索并注入 HintBlock）
- `agentscope.app.rag`：`CollectionPerKbManager`、`LocalBlobStore` / `S3BlobStore`、索引 worker、`/knowledge_bases` REST API

### 5.2 可复用 agent_study 的部分

| 可复用 | 原因 |
|---|---|
| `rag/common.py` 的解析/切片/embedding 批量逻辑 | 基于官方 parser/chunker，质量不错；`require_file=True` 防“路径当正文” |
| `rag/rag_registry.py` | SQLite 记录“哪个文件进了哪个库、用的哪个 embedding 模型”，对重建/排障有用 |
| `rag/rag_main.py` 的懒加载思路 | 单个后端依赖缺失不拖垮整个 RAG |
| 多后端适配器 | 只有确实要 zvec/chroma/faiss/pgvector/oceanbase/milvus 时才搬；不要默认全开 |

**不建议照搬：**

- 默认 `zvec` + 7 个后端全量依赖（当前 `.venv` 里 chromadb/faiss/pymilvus/qdrant/mem0/redis 都没装）
- `async_rag_tools` 的旧入口风格（没有统一函数白名单/未知 function 处理）
- 把检索做成普通工具再和 `RAGMiddleware` 重复

### 5.3 检索与写入分开

- **检索**：优先 `RAGMiddleware(mode="agentic"/"static")`，一个 `search_knowledge` 工具，自动跨多个知识库。
- **写入/删除/列表**：单独的管理 API 或 `tools/rag/` 工具；不要和检索混在一个多入口工具里。
- **多租户**：`KnowledgeBase(metadata_filter={"tenant_id": ...})`，官方保证 search/list/delete 不越界，insert 强制打标。

### 5.4 配置项建议

在 `config/schema.py` 增加（示例）：

```text
rag.enabled                  bool
rag.backend                  str      # milvus_lite/qdrant/...
rag.collection               str
rag.mode                     str      # agentic/static
rag.top_k                    int      # clamp
rag.score_threshold          float
rag.chunk_size               int
rag.overlap                  int
rag.embedding.provider       str
rag.embedding.model          str
rag.embedding.api_key        str      # secret, None
rag.embedding.base_url       str
rag.backend.url / host / port...      # 敏感项 None
```

仍遵守现有约定：**连接/身份类参数无源码兜底，data > sqlite > 400**。

### 5.5 分布式形态

如果以后做 Web 服务/多 worker：

- `AsyncSQLAlchemyStorage` + `RedisMessageBus`
- `CollectionPerKbManager` + `LocalBlobStore` / `S3BlobStore`
- `enable_index_worker=False` + 独立 `run_worker`
- 当前 `.venv` 已有 `sqlalchemy` / `asyncpg` / `fastapi` / `uvicorn`，但 **redis 未装**；先做单进程 SQLite + 本地向量库即可。
