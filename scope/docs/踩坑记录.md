# scope/tools 踩坑记录

分三类：**A 使用侧的坑**（调用工具时会撞）、**B agentscope 2.0.12 集成坑**（装配时会撞）、**C 我误诊过的坑**（避免你按错线索去修）。

每条都标了实测依据。

---

## A、使用侧的坑

### A1. 业务参数平铺顶层，不嵌 `arguments`

```python
{"function": "count_table", "table": "orders"}                    # ✅
{"function": "count_table", "arguments": {"table": "orders"}}      # ❌
```

错误表现极具误导性——不报"未知参数"，而是报 **「非法表名: None」**，让人以为是表名有问题。

根源：`main_db.py` 用 `args = {k: data[k] for k in (...) if k in data}` 从顶层挑键。

### A2. 错误字段是 `message`，不是 `msg`

```python
r = await async_db_tools(...)
r["msg"]        # ❌ KeyError，或 .get() 拿 None → 误判为"没报错"
r["message"]    # ✅
```

### A3. db 写工具的行数据键是 `data`，不是 `values`

```python
{"function": "insert_row", "table": "customers", "data": {"id": 3, "name": "王五"}}   # ✅
{"function": "insert_row", "table": "customers", "values": {...}}                      # ❌
```

内外双层 `data` 极易混：外层是 `data` 字典，内层行数据也叫 `data`。
依据：`args = {k: data[k] for k in ("database","table","filters","data","sql") if k in data}`。

### A4. `download` 是流式工具，直接 `await` 拿不到结果

六域里**唯一**的流式工具（`net/download.py` 有 5 处 `yield`，其余功能全是 0）。

```python
r = await async_req_tools({"function": "download", ...})
r.get("code")        # ❌ AttributeError: 'async_generator' object has no attribute 'get'
async for chunk in r: ...   # ✅ 自己迭代
```

经 agentscope `FunctionTool` 调用则**完全正常**——`_adapters.py` 显式识别 `AsyncGenerator` 并转成流：

```
chunk#1 state=running  已下载 0.0MB / 0.0MB (100%)
chunk#2 state=running  {"code": 200, "data": {"save_path": ..., "size": 1024, ...}}
chunk#3 state=success  （最终 ToolResponse）
落盘 1024 字节 ✅
```

### A5. 流式进度文本会污染最终工具结果（真缺陷）

承上，`Toolkit.call_tool` 的累积机制（`ToolResponse.append_chunk`）把所有块**拼成单个 TextBlock，无分隔符**：

```
'已下载 0.0MB / 0.0MB (100%){"code": 200, "data": {"save_path": "/tmp/dl.bin", ...}}'
```

**模型最终看到的不是合法 JSON**，若它试图解析会失败。

修法（择一，均需改工具侧）：
- 进度块改用 `ToolChunk(state=ToolResultState.RUNNING)` 且让最终块独立成块，避免拼接
- 或在进度与结果之间插换行/分隔标记
- 或 `download` 干脆不产进度（`report_every` 设为极大值），退化为一次性返回

这是 A4 与 agentscope 累积行为交互出来的问题，**原件与拆分版同样存在**，非拆分引入。

### A6. `cmd_run` 超时不算错误，须查 `timed_out`

超时返回 `code=200`，`message` 是「命令执行超时，已返回部分输出」。
只看 `code` 会把截断的输出当完整结果。

### A7. `cmd_run` 的布尔项容忍字符串 `"yes"`/`"on"`

`_common.get_common_args` 接受 `"true"/"1"/"yes"/"on"/"y"` 与对应否定写法。
若平台想严格化（只收真 bool），改这里，不要在 `cmd_run.py` 里加校验。

### A8. `find_email` 四个条件至少给一个

`keyword` / `subject` / `sender` / `date_from` / `date_to` 全空 → 400
「keyword / subject / sender / date_from / date_to 至少一个」。这是防无约束全箱扫描。

### A9. `mail/to_mail` 是 `send_email` 的兼容别名

`main_mail.py` 里两个分支路由到同一函数。**勿删**——删了会让历史调用方报"暂不支持的 function"。
（原代码即如此，非拆分引入。）

### A10. `net` 的文件闸门未注入时默认放行

`configure_fs_policy(check_write=..., check_read=...)` 不调用则闸门放行（高代码单机场景）。
**线上必须注入**，否则截图/PDF 抽取可写读任意路径。独立模式有兜底（仅允许 cwd），但那是兜底不是策略。

### A11. 可选依赖是延迟导入，构造成功 ≠ 能用

`crawl4ai`、`asyncpg`、`aiomysql`、`pymongo` 都在**函数内**导入。所以：

- 模块可加载、dispatcher 可路由、错误文案可返回
- 只在真正进入该分支时 `ModuleNotFoundError`

同理 agentscope 的 `QdrantStore()` **构造成功**，第一次调用才报缺 `qdrant_client`。
别被"导入通过/构造成功"骗了，要跑到那条分支才算验证。

### A12. mcp 全域没有入参类型检查，非 dict 直接裸抛异常

`tools/mcp/` 三个文件**零 `isinstance` 检查**（实测），传 `None` / `"notdict"` / `123` 一律：

```
File ".../tools/mcp/_config.py", line 37, in resolve_mcp_servers
AttributeError: 'NoneType' object has no attribute 'get'
```

`async_mcp_client` 与 `async_mcp_tools` 两个入口都如此。

对照其余四域（crawl/mail/net/system）的 `main_*.py` 都有首行防护：

```python
if not isinstance(data, dict):
    return {"code": 400, ..., "message": "错误：data 必须是字典对象"}
```

**mcp 是唯一的例外**。装配时若入参可能来自不可信来源（模型输出、前端），必须自己在调用点包一层，
否则异常会穿透到 agentscope 的事件流。

### A13. db 对 `None` 宽容，但对 str/list/int **裸抛未捕获异常**

`main_db.py` 用 `data = dict(data or {})` 而非 `isinstance` 检查，于是行为分裂成两种：

| 入参 | 结果 |
|------|------|
| `None` | ✅ 转成空 dict → 正常返回 400「未知 function: (空)」 |
| `"notdict"` | ❌ `ValueError: dictionary update sequence element #0 has length 1; 2 is required` |
| `123` | ❌ `TypeError: 'int' object is not iterable` |
| `[1, 2]` | ❌ `TypeError` |

`async_db_tools` 与 `async_db_write_tools` 都一样。原件与拆分版逐项一致（已对撞验证），**非拆分引入**。

危险点在于 `None` 能正常走通，容易让人误以为整个域都有防护，从而不去补检查——
实际字符串和列表入参会直接炸。

> **我此前的等价性测试漏了这个场景**：`db` 的 43 个用例全部是合法的 `(db_config, function, args)` 三元组，
> 没有覆盖非 dict 入参，所以这个缺陷直到补写文档时才被发现。
> 其余四域的测试**有** `None`/`"notdict"` 用例。
> 教训：**每个域的健壮性用例必须独立覆盖，不能靠"别的域测过"推断**。

### A14. db 表级管控启用时，`run_query` 只允许单条 select/with

未启用管控时，`run_query` 靠起始词白名单（`select/with/show/desc/describe/explain`）放行；
一旦 `allowed_tables`/`denied_tables` 生效，改走 sqlglot 解析，**无法完整解析即拒绝（fail-closed）**，
且错误文案变成「表级管控已启用，run_query 仅支持单条 select/with 语句」。

行为差异：同一个 `SHOW TABLES` 在无管控下可跑，有管控下被拒。启用管控前要先测一遍现有 SQL。

### A15. `_err` 的错误位置：改进的真实边界（此前我的描述被夸大）

`db/_helper.py:50` 的 `_err` 原实现后缀**硬编码** `_async_db_tools`，且 `__file__` 取 `_err`
自己所在文件，所以所有闸门拒绝、配置错误、SQL 校验失败都报同一个位置：

```
data: ".../tools/db/_helper.py_async_db_tools"     ← 实际是 gate.py 拒的
```

第二轮改为 `_err(msg, where)`，由调用方传自己的函数名。实测改进的**真实形状**：

| 场景 | 现位置标识 |
|---|---|
| 闸门拒绝 | `_helper.py__tbl_gate` |
| 配置错误 | `_helper.py__resolve` |
| SQL 执行失败 | `_helper.py__lt_read_run` |
| 表级校验 | `_helper.py__sql_tbl_check` |

⚠️ **文件层面仍是 `_helper.py`（信封层），只有函数名精确到了实际出处。**
我上一版文档写成「报实际出错模块（`gate.py`/`executors.py`…）」是**夸大的**——
`_err` 用 `__file__` 取的是它自己所在的文件，不是调用方的。

函数名层面已足够定位（`_tbl_gate` vs `_resolve` vs `_lt_read_run` 一眼区分闸门/配置/执行）。
要做到文件层面也精确，只有两条路，均未采纳：

- 调用方传 `__file__`：每个调用点多一个参数，噪音大
- `_err` 内用 `inspect.stack()` 自动取：闸门在 `list_tables` 的循环里逐表调用，
  栈内省的性能代价叠加在已经 2.2× 的信封开销上（见拆分规范的性能实测）

对比 `system` 这类**每函数自拼** `f"{__file__}_{fn}"` 的，文件与函数名都精确：

```
tools/system/cmd_run.py_cmd_run      ← 参数校验
tools/system/_common.py_cmd_run      ← timeout 归一化
tools/system/main_sys.py_async_sys_tools ← 路由
```

这是"信封集中一层"与"位置精确"之间的固有张力：**集中复用必然丢失调用方上下文**。
### A21. `download` 与 `screenshot` 的闸门**不对称**（已修）

crawl 独立成域时文件闸门只长在 crawl 侧，于是同一 net 能力出现两种命运：

| 功能 | 写文件方式 | 过闸门？ |
|---|---|---|
| `screenshot` | `open(save_path,"wb")` | ✅ `_check_write` |
| `extract_pdf` | 读 `pdf_path` | ✅ `_check_read` |
| **`download`** | `open(save_path,"wb")`（还先 `makedirs`） | ❌ **完全不过** |

危害：平台为租户注入 `check_write` 后，截图/PDF 受约束，而 `download` 能把文件写到
`uploads` 根之外——**同一份策略被一个工具绕过**，且从审计日志上看不出来。

crawl 合并回 net 后闸门提到 `net/_fs.py` 作**域共用层**，`download` 补上 `_check_write`，
且判定在 `makedirs` **之前**（建目录本身也是写操作）。实测同一路径两侧判定一致：

```
download cwd 之外   code=400 错误：保存路径被拒：超出可写入范围（scope 独立模式仅允许当前工作目录子树）
download cwd 之内   code=200 下载完成
同路径同判定        download 拒绝=True   screenshot 拒绝=True
平台注入生效        /tmp/ok → code=200；/etc/cron.d → code=400「租户策略拒绝」
```

⚠️ **这是行为变更**：合并前 `download` 写任意路径都能成功，现在 cwd 之外会被拒。
平台侧需注入 `check_write` 放开到自己的 uploads 目录，否则下载功能对老调用方失效。

### A22. `_err` 在两域**参数顺序倒置**（已消除）

合并前 `net` 与 `crawl` 的信封函数签名互为镜像：

```python
net/_client.py   _err(message, func_name="", code=400, prefix=None)
crawl/_helper.py _err(where, msg)                    # ← 顺序相反
```

两者前两个参数都是 `str`，所以**写反不会报错**，只会产出垃圾：

```python
_err("async_crawl", "错误：data 必须是字典对象")   # crawl 侧正确
_err("错误：data 必须是字典对象", "async_crawl")     # 若按 net 习惯写 → message 变成函数名、
                                                    #   data 变成中文文案，且 code 仍是 400
```

跨文件复制粘贴错误处理代码时最容易撞，且静态检查抓不到（类型完全合法）。
合并后全库统一为 `_err(message, func_name, code, prefix)`，此陷阱消失。

⚠️ 但**前缀约定仍不统一**（这是原件既有差异，刻意保留）：`crawl` 侧的 `_err` 原本不加前缀、
由调用方自带「错误：」；`net` 侧按 code 自动加。合并时统一为后者，
所以原 crawl 各调用点的「错误：」前缀被剥掉——若漏剥就会产出「错误：错误：x」（见 C4）。

## B、agentscope 2.0.12 集成坑

### B1. 模型必须传 `{"data": {...}}` 一层包裹

`Toolkit.call_tool` 把 `input` JSON **展开成 kwargs**，而这些函数签名是 `(data: dict)`：

```
input = {"function":"count_table"}          → async_db_tools() got an unexpected keyword argument 'function'
input = {"data":{"function":"count_table"}} → state=success ✅
```

这就是模型看到的 schema 是 `{"data": {"additionalProperties": true}}` 黑盒的由来——
`data` 是**参数名**，不是业务字段。六个域全部如此。

### B2. 自定义 FunctionTool 默认每次都要人确认

`tool/_adapters.py` 的 `check_permissions`：不给 `permission=` 参数就返回

```python
PermissionDecision(behavior=ASK,
                   message="Custom function tools must be explicitly allowed by the user.")
```

`PermissionMode.DEFAULT` 下每个工具调用都停在 `RequireUserConfirmEvent`。
要么传 `permission=PermissionDecision(ALLOW, ...)`，要么配 allow 规则，要么换模式。

### B3. 业务错误在 agentscope 侧记为 `success`

`_convert_func_result_to_chunk` 无条件给 `state=ToolResultState.RUNNING`，把返回值 JSON dump 成文本：

```
闸门拦下 DELETE → 工具返回 {"code":400,...} → agentscope state=success
```

后果：`InjectionConfig.tool_retries_limit`（同参数连续失败 3 次注入"别再重试"提示）**识别不到这类失败**，
重试逻辑形同虚设。想让闸门反馈可被模型感知，工具须返回 `ToolChunk(state=ERROR)` 或直接抛异常，
而不是塞 `code` 字段。

这是这批工具与 2.0.12 之间唯一的**语义断层**，也是重构 `db/schemas.py` 时最值得顺手解决的点：
结构化入参 + 显式 ERROR 状态，黑盒（B1）与错误识别（B3）一起消掉。

### B4. `get_tool_schemas()` 默认只见 basic 组

签名 `get_tool_schemas(groups=None)`，内部 `groups_filter = ["basic"] + (groups or [])`。
自己调时必须显式传 `state.tool_context.activated_groups`，否则以为"工具没挂上"。

`Agent` 内部走的是正确路径（`agent/_agent.py:3384`），只有手工调试时会踩。

### B5. `ToolCallBlock.input` 是 JSON 字符串

```python
ToolCallBlock(type="tool_call", id="t1", name="async_db_tools",
              input=json.dumps({"function": "count_table"}))   # ✅
              input={"function": "count_table"}                # ❌ ValidationError: Input should be a valid string
```

它是流式片段的累积缓冲，不是解析后的 dict。写测试、造迁移数据、手工重放工具调用时必踩。

### B6. 未激活组的工具报 `ToolGroupInactiveError`

这是**期望行为**，不是 bug——`state=error`，message 形如
`The tool 'async_sys_tools' in group 'sys' is currently inactive`。
验证工具组闸门是否生效，就看这一条。

## C、我误诊过的坑（别按错线索去修）

记录在此，避免后人重复排查。

### C1. ❌「`download` 缺 `save_path` 会崩 `AttributeError`」

**真相**：`download` 有完整校验（`net/download.py:38-40` 返回 400「data 中缺少 save_path 字段」），
不带 `save_path` 时行为完全正确。

误诊来源：等价性测试里两边都记为 `code=EXC AttributeError`，我据此判定是工具缺陷。
实际是**我的测试代码**对 async generator 调了 `.get()`（见 A4）。
"两边一致"当时是对的（等价性成立），但我把一致的原因归错了。

### C2. ❌「`db` 白名单缺陷导致 `list_databases` 恒空」——这条**是真的**，但位置要说清

`db/main_db.py:152` 与 `:155` 两侧不一致：

```python
out = [x for x in out if x in allow]                              # 白名单：精确匹配
out = [x for x in out if not any(_db_same(e, x) for e in deny_dbs)]  # 黑名单：_db_same（去后缀互认）
```

SQLite 文件夹模式下 `x` 是 `"orders.db"`，白名单条目按文档写 `"orders"`（可省后缀），
精确匹配必然落空 → **启用 `allowed_databases` 后 `list_databases` 恒返回 `[]`**，模型无法发现数据库。

实测：

| db_config | `list_databases` 返回 |
|---|---|
| 无白名单 | `["orders.db"]` |
| `allowed_databases: ["orders"]` | `[]` ← 缺陷 |
| 单文件 `path` 模式 | `["orders.db"]` |

注意 `_db_gate` 里（`gate.py:204-208`）白名单**是**走 `_stem` 互认的，所以直接指名查询、
表级管控都正常——只有 `list_databases` 的输出过滤这一处漏了。

修法：`main_db.py:152` 换成 `_db_same`，与黑名单统一。一行。
（`gate.py` 的 docstring 已留提示；此处原样保留未改，以维持与原件的等价性。）

### C3. ❌「`system` 的错误文案少了个空格是改进」

早期手写 `system/main_sys.py` 时用 `', '.join(FUNCTIONS)` 自动生成支持清单，
与原件的 `"支持: cmd_run "`（末尾多一个空格，是笔误）产生 1 处不等价。

后来统一改用机械切分（保留原 `if` 链与原文案），21/21 全等。
**教训**：为了"顺手改进"而偏离原件，会摧毁可证明性等价这一保证。
改进应当是独立的一次提交，不与拆分混在一起。


### C4. ❌「`_err` 统一加前缀」差点造出跨域双重前缀（第二轮）

第二轮把 `system`/`mail` 的路由错误从手写字典改成 `_err(...)`，而 `_err` 会给 400 加
「错误：」前缀——**原件这些文案本身已带或刻意不带前缀**，于是产出：

```
错误：错误：timeout 必须大于 0
错误：暂不支持的 function: bad，支持: ...     ← 原件此处刻意无前缀
```

第一处是纯 bug，第二处是跨域不一致（`net`/`crawl` 仍是手写无前缀）。
两道都是**等价性测试**抓出来的，不是靠肉眼——如果只看"能跑"，双重前缀会一路带到线上。

教训写进拆分规范：**改任一处 `_err` 语义，六个域全部复查**。最终解法是给 `_err` 加
`prefix` 参数（`None` 时按 code 定），路由文案用 `prefix=False` 保持原件形态，
而不是强行统一成一种前缀约定。

### C5. ❌ 归一化只做了新版一侧（第二轮）

对撞辅助函数时，我只对新版的 `data` 字段做了路径归一化，忘了原件那一侧，
于是 `system` 报出 7 项假差异（`<FILE>_cmd_run` vs `/mnt/.../async_sys_tools.py_cmd_run`）。
`db` 更严重：因 `_err` 的 `where` 也改了（A15 修复），连函数名后缀都不同，
必须用 `re.sub(r"/.*?\.py_.*", "<FILE>", v)` 连后缀一起抹掉。

**归一化必须双侧对称**，否则测的是"路径不同"而不是"逻辑不同"。

### C6. ❌ 批量改写脚本连吃两个 bug（第三轮）

本轮用 AST 脚本做 `_err` 参数顺序转换与 500 统一，踩了两个**静默破坏源码**的坑：

**① `col_offset`/`end_col_offset` 是字节偏移，不是字符偏移。**

```python
start = abs_off(src, node.lineno) + node.func.col_offset
end   = abs_off(src, node.end_lineno) + node.end_col_offset
```

源码含中文（UTF-8 每汉字 3 字节），当字符索引用会**多吃「汉字数 × 2」个字符**，
把 `_err(...)` 后面那条语句的开头啃掉：

```python
# 损坏结果
return _err("data 必须是字典对象", "_check_write")("path")     # 丢了 path = data.get
def _apply_wait_for(...)  的开头被吃掉，损坏跨到函数边界
```

正解：取 `ast.get_source_segment(src, node)` 拿整段源码，从行首 `src.find` 定位，
用 `len(seg)` 的**字符**长度定终点。

**② 正则替换吃掉了 `return` 关键字。**

匹配 `return \{"code": 500, ...\}` 却替换成 `_err(...)`，忘了带 `return`：

```python
    except Exception as e:
        _err(f"处理失败，原因：{e}", "getcityid", code=500)   # ← 没有 return
```

后果比 ① 隐蔽得多：**语法完全合法**，`py_compile` 通过，但函数在异常路径上返回 `None`，
agentscope 把它 JSON dump 成 `"null"` 文本给模型——**错误信息全丢，且看起来像正常返回**。
12 处中招。

两个 bug 的共性：**都是静默的**。① 靠 `py_compile` 立刻暴露（SyntaxError 满地），
② 靠静态检查的「未定义引用」间接暴露（因为我同时漏了 import `_err`）。
如果 ② 的 `_err` 当时已可调用，它会被**完全静默地**带上线。

教训：**批量改写源码的脚本，跑完必须立刻做 AST 级校验**（编译 + 未定义名 + 行为对撞），
不能只看"脚本没报错"。本轮的静态检查器救了 ②，这是它存在的意义。
